# Coolify plugin 1.0.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for
> tracking.

**Goal:** Ship release 1.0.0 of the `coolify` Termix plugin. That release includes the Foundation milestone
and the five additions the owner asked for in 1.0: companion plugins; metrics, traffic and the MCP client;
server updates; three-spec tracking; and the public status page.

**Architecture:**

- **Backend:** a plugin-API-2 backend process. Its parts:
  - a Coolify REST client generated from vendored OpenAPI specs
  - a small MCP JSON-RPC client
  - SSH helpers that run through `ctx.ssh`
  - services for connections, host sync, resources, containers, metrics, updates, companions and status pages
  - Express routes, operations, and the public status route on top of those services
- **Frontend:** a framed React frontend built from `@termix-ssh/plugin-sdk/ui`. It draws one main `coolify` tab,
  a `coolify-shell` tab that embeds SSH Terminal's `terminal.view`, and host surfaces.
- **Data:** connections, servers and other state live in the plugin's own tables. Tokens are sealed with
  `ctx.secrets.seal`.

**Tech Stack:**

- TypeScript (~7.0), React 19, Express 5 router, Drizzle through `ctx.db`
- Vitest with `@termix-ssh/plugin-sdk/testing`
- `openapi-typescript` (dev only) for generated types

**Spec:** `docs/superpowers/specs/2026-11-19-coolify-plugin-design.md`. Read it first. Section names below
refer to it.

## Global Constraints

**Identity and engine**

- Plugin id `coolify`, name "Coolify for Termix", category `Infrastructure`, icon `Rocket`, version `1.0.0`. The version
  is the same in `manifest.json`, `package.json` and the newest `CHANGELOG.md` section.
- `engine`: `{ "termix": ">=26.11.2-0", "api": "^2.7.0" }`.

**Termix plugin rules**

- Follow the hard rules in `node_modules/@termix-ssh/plugin-sdk/PLUGIN-GUIDE.md`:
  - No `.returning()`. Run `await ctx.db.persist()` after every write, `{ lazy: true }` for cache, events
    and recent rows.
  - Index only `varchar` columns.
  - Every UI string goes in `locales/en.json`.
  - Every route has an `@openapi` block, an `authz.json` entry, and a test with and without permission.
  - The user id comes only from `ctx.currentActor()`.
  - Outbound HTTP goes only through `ctx.fetch`, and SSH only through `ctx.ssh`.
  - Shell values go through `shellQuote()` from the SDK. Secrets go on stdin, never in argv.
- Capabilities are exactly the list in the spec's Capabilities table. `operations.invokes` lists exact ids,
  never `*`.
- Never return, log or put into an operation result any token, private key, env value, service token or
  status-page token. The one exception is a status page's URL, which carries its token: it is returned once,
  by the create and rotate responses (Task 18), and from the operations only as a `sensitive` output, which
  Termix drops before a run is stored or shown. It never appears in a summary, a log, history or any later
  response.
- Routes send 4xx for user errors. Coolify upstream failures become 502 `{ error, cause }`. Routes never
  throw, because of the five-errors-a-minute budget.

**Repo rules**

- Commits use Conventional Commits (commitlint) with no AI attribution lines (repo hook).
- Run `npm run format` before committing.
- Never run write, create or delete calls against the owner's production Coolify. Live checks are
  read-only. Use a throwaway Coolify in Docker for write paths.

**Done checklist (every task)**

Every task ends with these passing:

- `npm test`
- `npm run typecheck`
- `npm run validate`
- `npm run build`
- `npm run format:check`
- `npx termix-plugin migrations --check`

## Review Focus

Most likely first. Each line names the task whose tests pin it.

1. **Coolify answers with HTML or a redirect instead of JSON** (Cloudflare Access login page, reverse proxy
   error page, wrong URL). This should surface as a plain cause such as "behind Cloudflare Access" or "not a
   Coolify API", never as a JSON parse throw. Task 3.
2. **A shell, logs, metrics or updates request for a resource whose server has no linked host, or whose host
   was deleted.** This should answer 409 `{ cause: "not-linked" }` with the sync hint, never 500. Tasks 13
   and 15.
3. **Syncing the Coolify host (`host.docker.internal`) without an address override.** This should refuse
   that one row with `cause: "needs-address"` while the other rows still sync. Task 8.
4. **The container is not running, there are several candidates (compose), or none match the labels.**
   These answer 409 `not-running`, 300-style `{ choices }`, and 404 `container-not-found` respectively.
   Task 13.
5. **The token lacks `read:sensitive`.**
   - Logs fall back to SSH, labelled `source: "ssh"`.
   - Host sync uses mode B and asks for a credential.
   - The UI shows why.

   Tasks 9 and 14.
